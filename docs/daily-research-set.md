# 일일 전략 연구 세트 규약

## 목표와 적용 범위

Asia/Seoul 날짜 기준 하루 **전략 연구 세트 1개**를 완료한다. 한 세트는 하나의 핵심 가설 아래 기본형, 복수 변형/파라미터 최적화, 선택과 평가, 결론을 묶는다. 다른 날의 같은 가설 재검증도 새 세트로 만들고 원본 세트와 차이를 연결한다. 연구 성과가 좋을 때만 완료하는 것은 아니다.

이 문서는 작업 계약이다. 자동 실행기·스윕·데이터 snapshot·상태 검증기·스케줄러를 구현한 것이 아니다. 현재 CLI와 수동 파일 기록으로 수행 가능한 범위만 실행하고, 충족할 수 없는 조건은 blocked와 후속 이슈로 남긴다. 초기에는 cron을 등록하지 않는다. 실행·데이터 고정·완료 검증 도구는 #20, 일일 연구/주간 개선 자동화는 #21, IS-only 스윕은 기존 #16에서 추적한다.

## 식별자와 파일 계약

- 세트 ID: `<YYYY-MM-DD>_<slug>`; 날짜는 시작 시 KST로 고정한다.
- 전략 ID: `<set-id>__baseline`, `<set-id>__v001`, `<set-id>__v002` 등. 모든 실행 시도는 고유 ID를 가진다.
- 최소 구성: baseline 1개와 **서로 다른 파라미터/신호의 변형 2개 이상**. 같은 파일을 재실행하거나 이름만 바꾼 것은 변형 수에 넣지 않는다.
- TOML의 기존 필드만 사용한다. `tags`에 `set:<set-id>`를 추가하고, `parents`에는 실제 `ref()` 앙상블 부모만 넣는다. 새 필드를 Rust가 처리한다고 가정하지 않는다.

```text
research/<set-id>/
  plan.json           # 실행 전 확정; hermes/templates/plan.json에서 시작
  data-manifest.json  # 대상 파일 SHA-256, 기간, 종목, 기준시각, 품질/누락 기록
  attempts.jsonl      # 모든 실행/실패/중단 시도를 append-only로 기록
  logs/               # 시도 ID별 stdout/stderr; 인증정보는 절대 저장하지 않음
  selection.json      # IS만으로 선택하고 해석 전에 고정
  report.md           # 상태, 비교표, 결론, 한계, 다음 실험과 관련 이슈
strategies/<set-id>__*.toml
results/<run-id>.json  # 성공 실행의 상세 곡선; CLI 생성
results/index.json    # CLI 생성 공유 인덱스; 기존 엔트리는 보존
```

템플릿은 빈 양식이다. null/TODO/예시를 실제 실행 결과로 오인하지 않는다. `research/`는 아직 대시보드의 입력이 아니다. 파일 해시는 터미널/Python으로 계산하며 추정하지 않는다. 재현에 필요한 원본 데이터/캐시 snapshot은 gitignored 로컬 저장소 등 안전한 위치에 보존하고 manifest에 위치와 해시를 기록한다. 원본 보존이 불가능하면 그 한계를 기록하고 재현 가능하다고 주장하지 않는다.

## 제한된 데이터의 비공개 증거

토스 등 재배포가 제한된 공급자는 [비공개 데이터 규약](toss-data.md)을 따른다. 원본 수치·OHLCV·곡선·상세 성과·수치가 든 로그는 Git checkout 외부의 권한 제한 경로에 보존한다. 공개 연구 디렉터리의 manifest/attempts/selection/report에는 허용된 메타데이터와 private 원본의 SHA-256만 포함할 수 있다. 실제 private plan·데이터 manifest·시작/종료 로그·IS 선택 근거·시장별 비교 보고서가 존재하고 검증돼야 하며, 공개 수치를 생략한 것을 실험 생략의 근거로 사용하지 않는다.

공개 plan에는 가설·전 후보/기준·예산·engine revision·private manifest 해시·위치 별칭을 고정한다. selection에는 후보 ID·IS-only 선택 규칙·전체 성공/실패 목록·private 선택 증거 해시를 포함해 커밋/push한 뒤 평가한다. 공개 report에는 정성 결론·상태·제약·후속 이슈와 private 수치 보고서 해시를 남긴다. 출력 경로는 신규 `--data-manifest`/`--output-dir` 모드로 분리하고 공유 공개 results index는 수정하지 않는다. 이 예외는 미노출 holdout을 제공하지 않으며 기존 OOS 노출 고지를 유지한다. 상세 로컬 경로/비밀정보를 공개 메타데이터에 넣지 않는다.

기존 차단 manifest/audit/report는 덮어쓰지 않고 새 데이터 버전과 보고서 addendum으로 재개 이력을 연결한다. 코드 변경은 engineering 브랜치에서 검증·고정한 후 연구 브랜치로 비교 경계를 옮기며 연구 중 엔진/비용/split을 수정하지 않는다.

## 시작과 동시 실행 방지

1. repo 루트의 AGENTS.md와 현재 이슈·열린 PR을 확인한다. 전용 checkout/worktree와 `research/<set-id>` 브랜치를 사용한다. dirty checkout은 보존하고 충돌 작업을 중단한다.
2. 같은 날짜의 로컬 research 디렉터리와 원격 연구 이슈/PR을 함께 확인한다. 완료 세트가 있으면 종료하고, 진행/차단 세트가 있으면 동일 세트를 재개한다. 날짜가 달라진 재개 작업은 원래 ID를 유지하고 실제 실행 날짜도 기록한다.
3. 같은 세트에 동시 writer를 두지 않는다. 임시 실행 잠금은 원자적 생성과 finally 해제로 구현해야 하며, 소유 PID/호스트를 확인하지 않고 잠금을 삭제하지 않는다. 현재 자동 잠금은 미구현이므로 병렬 예약 실행을 금지한다. 경쟁 가능성을 해소할 수 없으면 blocked다.
4. 이슈 양식으로 연구 추적 feature 이슈를 연결한다. 이미 있는 이슈/PR을 재사용하고 중복 생성하지 않는다.

## 사전 계획

첫 전략 실행 전에 plan을 완성하고 commit/push한다. 데이터 준비가 선행되어야 한다. 다음을 계획에 명시한다.

- 가설, 이전 세트·교훈, 선택 이유, 예상 작동/실패 조건.
- baseline과 모든 사전등록 변형의 ID·파라미터·신호, 탐색 순서와 유한한 범위.
- 대상 시장/유니버스/기간, IS/OOS 경계, benchmark, 비용·체결 등 엔진 규칙의 코드 revision.
- 선택 지표의 정확한 식/방향·대상 시장·동점 기준. 기본형을 포함해 **IS만** 사용한다.
- 최종 평가 지표와 accept/defer/reject 조건. reject도 정상적인 완료다.
- 실행 예산과 종료 조건. 초기 기본값은 **baseline 포함 최대 12회 실행 시도, 최대 120분**, 최소 성공 3개다. 실패도 실행 수에 포함한다. 다른 예산은 실행 전 계획에 근거와 함께 고정한다. 예산 확대를 성과 확인 후의 탈출구로 사용하지 않는다.
- engine commit, 잠금파일 해시, 실제 데이터 manifest와 snapshot 위치, 데이터 노출 이력.
- 변경/수리 정책. 실행한 전략은 불변이며 실패 수리는 새 ID를 사용한다. 수리 최대 3회도 전체 예산 내에서만 허용한다.

계획 변경은 기존 내용을 덮어쓰지 말고 별도 revision과 사유를 남긴다. 관측 후 탐색/선택/채택 기준 변경이 필요하면 현재 세트를 blocked 또는 원래 기준으로 결론 내린 뒤 다음 세트에서 재계획한다.

## 데이터·엔진 고정

현재 `data::load`는 로컬 날짜가 오늘인 캐시를 재사용하고, 오래된 캐시는 갱신을 시도한다. 갱신 실패 시 stale 캐시를 쓰거나 종목을 건너뛸 수 있다. 따라서 캐시 폴더가 존재한다는 것만으로 데이터 고정·전체 유니버스 검증이 된 것은 아니다.

- 실행 전에 계획한 종목의 읽을 수 있는 캐시, 날짜 범위/품질, SHA-256, 실제 대상 목록을 manifest에 기록하고 재현용 snapshot을 보존한다.
- 매 실행 전후 해당 파일·종목 목록을 대조하고 stderr의 skip/stale/cache 오류를 확인한다. 원치 않는 갱신·누락·엔진 변경은 blocked다. 엔진 코드와 `Cargo.lock`도 동일해야 한다.
- `TZ=Asia/Seoul`인 동일 환경에서 수행한다. 세트 중 날짜가 바뀌거나 캐시 갱신이 일어나면 재현 조건을 확인하기 전에는 계속하지 않는다.
- 토스는 `tools/prepare_toss.py`의 data-only 준비와 `run --data-manifest ... --output-dir ...` frozen 모드를 사용한다. 기본 Yahoo 경로는 기존 자동 캐시 정책을 유지한다. 어느 모드든 입력 고정/품질을 확인할 수 없으면 `data_setup` 블로커로 기록하고 별도 준비 작업을 선행한다. 전략 실행을 몰래 준비 단계로 써서 미등록 실험 결과를 만들지 않는다.
- 뉴스는 뉴스 기반 가설일 때 필수다. 그 외 뉴스 수집 실패는 경고로 남기고 계속할 수 있다. 뉴스의 해당 시점 가용성도 입증하지 못하면 미래정보 없는 입력이라고 주장하지 않는다.

## 실행과 시도 기록

명령은 `hermes/SKILL.md`의 실제 CLI만 사용한다. 각 시도는 attempts.jsonl에 최소 다음 필드를 남긴다.

`run_id`, `role`(baseline/variant/repair), `parameters`, `signal`, `strategy_sha256`, `command`, `started_at`, `finished_at`, `exit_code`, `status`(ok/failed/interrupted), `engine_commit`, `data_manifest_sha256`, `result_path`, `log_paths`, `error`.

시작 이벤트를 먼저 기록하고 종료 이벤트를 같은 run_id로 append하여 실행 중 프로세스가 끊겨도 시도가 사라지지 않게 한다. 필드가 아직 없으면 null로 남기되 최종 보고서에서 미완료 시도를 명시한다. 성공한 결과만 나열하지 않는다. 선택 시에는 종료 이벤트와 실제 결과 파일을 대조한다.

CLI `run`/`fail`은 같은 ID의 결과를 교체할 수 있으므로 에이전트가 기존 ID 실행을 금지한다. `lesson`은 현재 세트가 새로 만든 결과에만 허용한다. 공유 index의 기존 엔트리를 보존하며 다른 세트의 파일은 수정하지 않는다.

## 최적화·선택·평가 경계

1. baseline과 사전등록 변형들을 유한한 예산 내에서 실행한다. 단계형 탐색이라면 다음 후보를 정하는 IS-only 규칙까지 사전 계획에 정의한다.
2. 정상 실행된 baseline + 최소 2개 변형이 있어야 완료 후보가 된다. 필요한 모든 사전등록 시도를 마치거나 사전 정의한 조기종료 조건을 충족해야 한다. 예산을 소진한 것 자체는 완료 조건이 아니다.
3. plan의 IS 선택·동점 기준에 따라 후보를 정한다. 불리한 시도도 비교표에 포함하고, 인접 파라미터의 민감도를 기록한다.
4. 선택 시점과 당시의 전체 시도 목록, plan/데이터 해시, 선택 이유를 selection.json에 기록하고 commit/push한다. 이를 고정한 뒤 기존 결과의 OOS를 최종 해석한다. 불필요한 재실행은 하지 않는다.
5. **현재 CLI는 모든 실행에서 IS와 OOS를 동시에 계산·출력·저장한다.** 결과를 가리거나 IS만 읽는 절차는 기술적 holdout 격리가 아니다. 현 프로토콜은 `holdout_status: exposed`를 사용한다. 이미 본 OOS의 후보 순위/파라미터 최적화 사용은 금지한다.
6. 최종 보고서에 IS/OOS와 baseline/Buy&Hold를 구분하고 실제 제공 지표(CAGR, Sharpe, MDD, excess CAGR 등)를 사용한다. benchmark Sharpe 등 CLI가 제공하지 않는 수치는 실제 계산 근거 없이 만들지 않는다.
7. 반복적으로 관측한 고정 OOS는 독립 검증이라고 부르지 않는다. 새 가설을 이전 OOS에서 얻었으면 그 영향을 기록한다. IS-only sweep 지원은 #16, 미노출 최종 holdout/워크포워드와 자동 검증은 후속 개발 대상이다.

## 완료·차단 판정

상태는 `planned` → `running` → `completed` 또는 `blocked`다. blocked는 원인 해결과 증거 기록 후 같은 ID로 재개할 수 있다. completed 산출물은 불변이며 정정은 별도 addendum으로 남긴다.

completed에는 **모두** 필요하다.

- 사전 계획과 고정된 엔진/데이터 provenance.
- 성공한 baseline + 최소 2개 서로 다른 변형, 예정 시도/정당한 종료 조건 충족, 전체 시도/실패 기록.
- IS 기준 후보 선택과 고정된 selection, OOS 노출 고지, 최종 비교·민감도·한계.
- `conclusion: accept | defer | reject`, 근거, 교훈, 구체적인 다음 실험.
- 미해결 버그/남은 기능은 프로젝트 양식의 기존/신규 이슈로 연결.

blocked는 `conclusion: null`, 원인, 완료하지 못한 단계, 실제 부분 결과, 재개 조건, 관련 이슈를 남긴다. 데이터/코드 오류·실행/예산 부족을 reject/defer로 위장하지 않는다. completed일 때만 해당 backlog를 체크한다. 하루 마감 시 미완료는 그대로 보고하며 가짜 완료를 만들지 않는다.

## 개발·게시·주기적 개선

- 하루 연구가 최우선이며 시스템 개선은 분리한다. 연구를 막는 정확성/데이터/재현성 문제는 즉시 이슈화하고 먼저 해결한다. 그 외 개선은 주간 검토에서 우선순위를 정한다.
- proposal은 자동 구현 승인이 아니다. 사용자가 승인한 feature/범위 내에서 별도 개발 브랜치·테스트·PR로 진행하고 활성 PR과 충돌하지 않는다.
- 이슈·작업 브랜치 push·PR 생성은 승인 범위다. main 병합/자동병합·배포·릴리스·파괴적 변경·실거래는 별도 승인을 받는다. PR 생성만으로 이슈를 완료 처리하지 않는다.
- 허용된 경로만 명시적으로 stage한다. 광범위한 `git add .`나 main 직접 push를 하지 않는다. 원격 이슈/PR/head SHA/파일 목록을 read-back한다.
- 로컬 세트 완료와 main 반영 상태를 구분해 보고한다. 세트 완료로 main 배포가 자동 승인되는 것은 아니다.
- 스케줄러 구성은 별도 작업이다. 매일 연구/주간 개선을 문서화한 사실과 실제 자동 실행 상태를 구분한다.
